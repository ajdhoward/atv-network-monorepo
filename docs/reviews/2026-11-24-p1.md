## Found and fixed here

`pnpm streams --probe` could not follow the link P1's resolve answers for a Drive channel. The ticket is
`/api/stream/<id>?exp&sig` — a path, deliberately, because the TV's `<video>` resolves it against the page and
only the host that minted it can verify the signature. Node's `fetch` has no page to resolve against and throws
`Failed to parse URL`, so the audit reported **every Drive channel as an unreachable link on exactly the
deployment where the proxy works**. The suite stayed green because its fixture handed the probe an absolute
`http://127.0.0.1:<port>/stream.m3u8`, which is not the shape resolve returns.

The probe now resolves against the audited origin, and the fixture carries a hostless ticket the way resolve
really answers: the new test fails without the change and passes with it. `39f5a7a`.

Two things this changes about how the audit is read:

- On a deployment **without** `ATV_STREAM_SIGNING_KEY`, resolve still answers the stored Drive share link. The
  probe follows it, Drive answers an HTML sign-in/download page, and the audit fails it as `answered HTML` —
  the same shape as the existing `atv-login` case. So `--probe` is the check that sees a proxy deployed but
  dead, and a plain run is not.
- With the key set, a probe now follows the ticket to this Worker, which fetches Drive, so a probe failure can
  be this Worker's `502 upstream_error` rather than Drive's own status. Both read as `link answered HTTP 502`.

## Rejected

- **Making `--probe` follow the ticket all the way to Drive's bytes** (a second hop, asserting a media
  content-type). It would catch a signing key that verifies but cannot reach Drive — which the Worker's own
  502 already reports — at the cost of downloading a byte range through the proxy on every audit, and it hides
  which side failed. The one hop plus the Worker's status is enough to tell an operator where to look.
