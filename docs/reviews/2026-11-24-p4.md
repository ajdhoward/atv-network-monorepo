## Answers

1. **Did `AGENTS.md` cost more than it saved?** It held at 209 lines and nothing in it read as ceremony this
   window. The line that earned itself again was "report untested paths as untested": the record below separates
   what ran against a real Worker from what only ran in a fixture, and that distinction is the review's useful
   half.
2. **A rule broken habitually?** Not in the files, but in the checks' reach: both scripts were changed together
   with the codes they read, and the matrix gained a row for each. What never happened was a run against a
   Worker that answers a 503 for a reason other than a missing signing key. The lesson from the fourth review —
   a check is only as honest as the states it has seen — was applied to continuity and not to these two scripts.
3. **Collisions or idling?** Neither. One agent, disjoint paths.
4. **Did a check pass while the thing it guarded was broken?** Yes. `/api/resolve` had answered
   `503 device_token_invalid` and `503 stream_unconfigured` since `2c06b68`, the README and the parity matrix
   named both, and both `pnpm streams` and `pnpm smoke` still keyed their explanation on the **status**. On a
   deployment whose household token contained whitespace, the audit said "no signing key" and sent the operator
   to set a secret that was already set. Nothing could catch it: every fixture produced one 503. `6233cbf`
   reads `code`, and three tests now hold one batch 503, one per-id 503 and the token fault's stop.
   Verified rather than argued this time, against real Workers in workerd: with a whitespace `ATV_DEVICE_TOKEN`
   smoke fails exactly one check (`GET /api/resolve — HTTP 503 device_token_invalid — the worker's
ATV_DEVICE_TOKEN contains whitespace…`) and `pnpm streams` stops after one request with the same sentence,
   while `/api/stream`'s `stream_unconfigured` check still passes on the same Worker — so the two codes are not
   being conflated in the other direction. A control Worker with a presentable token and a real Drive link but
   no signing key answers `503 stream_unconfigured (this deployment has no ATV_STREAM_SIGNING_KEY)`, smoke
   19/19. The signing-key diagnosis still fires for its own code.
5. **Is the backlog honest?** Mostly, and two entries had gone stale: P1's done paragraph and L4 both still said
   a Drive channel with no signing key "resolves to its unusable link". P5 made that false. L4's own premise —
   that a resolve `200` only proves a link is stored — is exactly what P5 removed, so both are corrected below.
   The rest is honest: nine blocked items are still blocked on the operator's hands or credentials, and R1 is
   still the one accepted decision waiting to be executed.
6. **What would the next session rediscover?** That `/api/health`'s `deviceTokenSet` is presence, not
   presentability: it reads `true` on the whitespace-token Worker that refuses every request. That
   `driveFileId` accepts only a realistic id (`[A-Za-z0-9_-]{10,}`), so a toy id like `abc` bypasses the proxy
   and resolves as a plain link — which is how this review's first control run misled itself. That `wrangler
dev` needs a free port and leaves a `workerd` child whose port survives killing the `pnpm` parent, so it has
   to be killed by the PID holding the port. That this workspace's `node_modules/.bin` can come back empty
   after a restore while `pnpm exec` still resolves from the store, and `npx`-based scripts then fetch a
   different wrangler; `pnpm install --frozen-lockfile` fixes it. That `ci:worker` outlives the five-minute
   command cap, so it has to be started detached and polled.
7. **Is the context file current?** It is, and it now carries the real-Worker token verification and this
   record. It still does not claim a TV, Drive itself or the on-screen keyboard.
